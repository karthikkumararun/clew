## ADDED Requirements

### Requirement: Editable query results
A result in the console Result tab SHALL be editable when its columns can be traced to one table (the edit target) whose complete primary key, or failing that a unique key of non-null columns, is present among the result's columns, the connection is not read-only for the session, and the target is a table (not a view). While a result is editable, a chip next to the result tabs SHALL read "Editing <schema.table> · key <columns>" in the accent colour (as in `design/canvas/ResultEditing.dc.html`), and the grid SHALL show the editing controls.

#### Scenario: Single table with its key
- **WHEN** the user runs `SELECT id, status, total FROM orders WHERE status = 'pending'` and `id` is the primary key
- **THEN** the chip reads "Editing public.orders · key id" and cells of `status` and `total` can be edited

#### Scenario: Aliased and reordered columns
- **WHEN** the query is `SELECT total AS amount, id AS order_id FROM orders`
- **THEN** the result is editable, and an edit of `amount` updates `orders.total` keyed by `order_id`

#### Scenario: Expression columns stay read-only
- **WHEN** the result includes `total * 1.2 AS with_tax`
- **THEN** that column is dimmed with a lock in its header and cannot be edited, while the other columns can

#### Scenario: Key columns of existing rows
- **WHEN** the user tries to edit the primary key cell of a row that came from the database
- **THEN** the cell is read-only with the reason "Key columns can't be changed", while key cells of rows inserted in this result can be edited

#### Scenario: Generated and identity columns
- **WHEN** a column is `GENERATED ALWAYS` or a computed column in the database
- **THEN** it is read-only in the result; columns that are `GENERATED BY DEFAULT` can be edited

### Requirement: Source detection
Clew SHALL determine the edit target from the driver's column provenance. When the driver reports none, Clew SHALL infer it by parsing the statement: exactly one table in `FROM` without joins, subqueries in `FROM`, `GROUP BY`, `DISTINCT`, `UNION`, `INTERSECT`, `EXCEPT` or window functions; plain column references (optionally aliased) map to that table's columns; everything else is read-only. When a statement cannot be parsed, the result SHALL be read-only. Key and generated-column information SHALL come from the introspection cache, loaded on demand.

#### Scenario: Oracle simple select
- **WHEN** an Oracle console runs `SELECT id, status FROM orders`
- **THEN** the source is inferred as `orders` and the result is editable if `id` is the key

#### Scenario: DISTINCT is not editable
- **WHEN** the statement is `SELECT DISTINCT id, status FROM orders`
- **THEN** the result is read-only with the reason "Aggregate or computed result"

#### Scenario: Unparseable statement
- **WHEN** the dialect-specific syntax cannot be parsed
- **THEN** the result is read-only with "Can't tell which table these columns come from"

#### Scenario: Views
- **WHEN** the source is a view
- **THEN** the result is read-only with "<schema.view> is a view"

### Requirement: Read-only reasons
When a result is read-only, the chip SHALL state the specific cause and, where one exists, the fix: the key is missing from the result ("No primary key in the result for orders. Add id to the SELECT."), the result combines several tables ("Choose table"), the session is read-only (with "Switch to read-write" as described in production-safeguards), an aggregate or computed result, a view, or unknown origin. Hovering a read-only column header SHALL give that column's reason.

#### Scenario: Key missing
- **WHEN** the query is `SELECT status, total FROM orders` and `orders` has primary key `id`
- **THEN** the chip says no primary key is in the result and names `id`, and cells cannot be edited

#### Scenario: Read-only production session
- **WHEN** the session is read-only on a production connection
- **THEN** the chip says "This session is read-only (PRODUCTION)" with a "Switch to read-write" action

#### Scenario: No key anywhere
- **WHEN** the source table has no primary or unique key
- **THEN** the chip says the table has no key and that rows can't be identified (Oracle ROWID, PostgreSQL ctid and SQLite rowid are not used for results)

### Requirement: Choosing the table in a joined result
When a result combines columns of several tables, the chip SHALL offer "Choose table". The menu SHALL list each table whose whole key is in the result as available and each other table as unavailable with the missing key shown ("key missing (add u.id)"). Choosing a table makes that table's columns editable and dims the columns of the others. When only one table qualifies it SHALL be chosen automatically. Rows can be added only when the result contains columns of a single table.

#### Scenario: Two candidates
- **WHEN** a join returns `o.id, o.status, u.id, u.name`
- **THEN** the chip offers both `orders` and `users`, defaults to the first table in `FROM`, and switching changes which columns are dimmed

#### Scenario: One candidate
- **WHEN** a join returns `o.id, o.status, u.name` (no `u.id`)
- **THEN** `orders` is chosen automatically and `u.name` is dimmed

#### Scenario: Add row in a join
- **WHEN** the result combines two tables
- **THEN** Add row and Clone row are disabled with "Rows can only be added to single-table results"

### Requirement: Editing cells
In an editable result the user SHALL edit a cell with Enter, F2 or double-click, using the editor for its type (text, number, boolean toggle, enum dropdown, date and time picker, JSON editor, binary via the value editor), with Tab and Enter moving to the next cell, Esc cancelling, and the context actions Set NULL (Mod+Alt+N), Set DEFAULT (Mod+Alt+D) and, for UUID and text columns, Generate UUID. Invalid input SHALL be refused with a message in the cell and never staged.

#### Scenario: Change a cell
- **WHEN** the user changes `status` of order 88213 from `pending` to `shipped`
- **THEN** the cell shows the edited colour and ring, the row is tinted, and the pending bar says "1 pending change"

#### Scenario: Wrong type
- **WHEN** the user types "abc" into a numeric cell
- **THEN** the editor shows "Not a number" and the value is not staged

#### Scenario: Set NULL on a NOT NULL column
- **WHEN** the user sets NULL on a column that does not allow it
- **THEN** the action is hidden from the menu for that column

### Requirement: Adding, cloning and deleting rows
In an editable single-table result the user SHALL add a row (toolbar, Mod+N), clone the selected rows (toolbar, Mod+Shift+D), and delete the selected rows (toolbar, Mod+Backspace). A new row starts with DEFAULT in the key and generated columns and NULL elsewhere; a cloned row copies all values except key columns that are generated or auto-numbered, which become DEFAULT. Deleting stages the removal, shows the rows struck through and removes nothing until submit.

#### Scenario: Clone
- **WHEN** the user clones the row with id 88213
- **THEN** a new green row appears with the same values, `id` set to DEFAULT, and the pending bar counts one insert

#### Scenario: Delete
- **WHEN** the user deletes two rows
- **THEN** both are struck through with a red marker and the pending bar counts two deletes

#### Scenario: Delete in a join
- **WHEN** the user deletes a row of a joined result
- **THEN** a confirmation says it deletes one row of the edit table and names how many result rows show it

### Requirement: Shared rows
When the same key of the edit table appears in several result rows (for example after a join that fans out), the result SHALL treat them as one table row: an edit made in one result row SHALL be mirrored in all of them, a notice SHALL say "Order 88213 appears 3 times in this result. An edit applies to all 3.", and one statement SHALL be generated.

#### Scenario: Fan-out join
- **WHEN** a join shows order 88213 on three rows and the user changes its status in one of them
- **THEN** all three rows show the new status and the pending bar counts one change

### Requirement: Pending changes
Staged changes SHALL be shown as in the table editor: edited cell on `--grid-edited-cell` with an accent ring and the row on `--grid-edited-row`, inserted row on `--grid-inserted-row` with a green "+", deleted row on `--grid-deleted-row` struck through with a red "−". A pending bar SHALL show "<n> pending changes", the breakdown, and Preview SQL, Revert all, Submit (Mod+Enter) and, in manual transaction mode, Submit and commit (Mod+Alt+Shift+Enter). Mod+Z and Mod+Shift+Z SHALL undo and redo staged changes, Mod+Alt+Z SHALL revert the selected cells or rows, and each result tab (including each result of a script) SHALL keep its own pending changes.

#### Scenario: Preview
- **WHEN** the user presses Preview SQL
- **THEN** the exact statements are listed, each keyed by the primary key and guarded by the old values of the edited columns, with Copy and "Open in console"

#### Scenario: Revert selected
- **WHEN** the user selects two edited cells and presses Revert selected
- **THEN** only those cells return to their loaded values and the pending count drops

#### Scenario: Leaving with pending changes
- **WHEN** the user re-runs the statement, runs another statement into the same result tab, closes the console tab or navigates pages with pending changes
- **THEN** a dialog offers Submit, Discard and Cancel

### Requirement: Submit and transactions
Submit SHALL send the staged changes in one batch as generated parameterised statements. In auto-commit mode the batch SHALL run in its own transaction and commit. In manual mode the batch SHALL run inside the console's open transaction (beginning one if none is open) wrapped in a savepoint: on success the statements stay in the transaction and the transaction's statement counter increases; on any failure the savepoint SHALL be rolled back so the transaction is exactly as before the submit, and all changes SHALL stay staged. Submit and commit SHALL submit and then commit. Commit and Roll back SHALL be available in the result's pending bar after a submit and in the console toolbar.

#### Scenario: Auto-commit submit
- **WHEN** the console is in auto-commit mode and the user submits 3 changes
- **THEN** they are applied and committed, the markers clear, and the rows are reloaded

#### Scenario: Manual mode submit
- **WHEN** the console is in manual mode and the user submits
- **THEN** a message says "Sent to the open transaction: 3 UPDATE, 1 INSERT, 1 DELETE. Not saved until you commit." with Commit and Roll back, and the toolbar shows the new statement count

#### Scenario: Failure keeps the transaction
- **WHEN** one statement violates a NOT NULL constraint during a manual-mode submit
- **THEN** the failing row is highlighted with the database message, nothing of this submit remains in the transaction, earlier statements of the transaction are untouched, and all changes stay staged

#### Scenario: Submit and commit
- **WHEN** the user presses Submit and commit in manual mode
- **THEN** the statements run and the whole open transaction is committed

#### Scenario: Row changed by someone else
- **WHEN** an edited row's old values no longer match the database
- **THEN** the batch is not applied, a dialog says "1 of 5 changes didn't apply" naming the row and the current value, and offers Keep editing, Reload row and Overwrite (re-submit that row without the old-value check)

### Requirement: After submit
After a successful submit the result SHALL show the saved values: edited rows are read back by key and replaced in the grid (so defaults, triggers and generated values appear), inserted rows receive their generated keys, deleted rows disappear, and pending markers clear. Columns that are computed from other columns SHALL be marked out of date (italic with a tooltip) and a "Re-run" action SHALL be offered, with a setting to re-run automatically when the result has at most 1,000 rows.

#### Scenario: Generated key appears
- **WHEN** an inserted row is submitted and the database assigns `id` 88232
- **THEN** the row shows 88232 and is no longer marked as new

#### Scenario: Stale computed column
- **WHEN** `total` is edited and the result has `total * 1.2 AS with_tax`
- **THEN** `with_tax` is shown italic as out of date until the statement is re-run

### Requirement: Safeguards apply
Submitting from a result SHALL follow production-safeguards: read-only sessions cannot submit (the result is read-only), "confirm writes" shows the statements and an estimated row count before they run (as in the Confirm writes dialog), typed confirmation applies to dangerous statements, and manual commit defaults apply. The AI assistant SHALL NOT be able to stage or submit changes in a result.

#### Scenario: Confirm on production
- **WHEN** the user submits on a production connection with confirm writes on
- **THEN** a dialog lists the statements with "≈1 row" per statement and runs them only after Confirm, with Cancel as the default

### Requirement: Result shortcuts
With focus in an editable result grid: Mod+Enter submits (while focus in the SQL editor Mod+Enter still runs the statement), Mod+Alt+Shift+Enter submits and commits, Mod+N adds a row, Mod+Shift+D clones, Mod+Backspace deletes, Mod+Z and Mod+Shift+Z undo and redo, Mod+Alt+Z reverts the selection, Mod+Alt+N sets NULL, Mod+Alt+D sets DEFAULT. All SHALL be registered in the shortcut registry in the grid scope and shown in the tooltips with the platform's symbols.

#### Scenario: Mod+Enter by focus
- **WHEN** the editor has focus and the user presses Mod+Enter, then the grid has focus with pending changes and the user presses Mod+Enter
- **THEN** the first runs the statement and the second submits the pending changes

### Requirement: Large and multiple results
Editing SHALL work on the rows loaded so far, keyed by primary key, and SHALL survive sorting, local filtering, find, transposing and loading further rows. A script producing several results SHALL give each its own edit target, chip and pending changes.

#### Scenario: Pending change in a filtered-out row
- **WHEN** the user edits a row and then applies a local filter that hides it
- **THEN** the change stays staged, is still counted, and the filter bar notes "1 pending change is in a hidden row"
